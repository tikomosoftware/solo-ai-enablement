# 第2回 参加者向けメモ: 小さな修正を依頼してみる

このメモは、第2回「小さな修正を依頼してみる」の事前・事後に参加者へ共有するためのものです。

## 今日の目的

Claude Codeに、小さな修正を安全に依頼する流れを確認します。

大事なのは、AIに作業を丸投げしないことです。
変更前に計画を確認し、修正後に差分と確認方法を見てから採用します。

## 事前に考えておくこと

自分の担当範囲で、影響が小さい修正候補を1つ考えておいてください。

おすすめの題材:

- READMEや手順書の補足
- 分かりにくい文言の修正
- 小さな不具合の再現確認
- テスト追加候補の洗い出し
- 影響範囲が1〜2ファイルに収まりそうな修正

避ける題材:

- 大きなリファクタリング
- 複数機能をまたぐ仕様変更
- 本番環境や本番DBへの操作
- 秘密情報を含むログや設定
- 削除、履歴操作、force pushなどの戻しにくい操作

迷う場合は、説明会の担当者やAI推進担当・相談窓口に先に相談してください。

## 最初に使う依頼文

以下を、自分の題材に合わせて書き換えて使えます。

```text
このリポジトリで、[修正したいこと] をしたいです。
まず変更は行わず、以下を整理してください。

1. 実装方針
2. 触る予定のファイル
3. 影響範囲
4. テストや動作確認の方法
5. リスク、不明点、今回やらない方がよいこと

こちらが確認してから、実装に進んでください。
```

## 計画を見たあとに確認すること

Claude Codeが計画を出したら、次の観点で確認します。

- 目的に合った修正になっているか
- 触る予定のファイルが多すぎないか
- 確認方法が具体的か
- リスクや不明点が書かれているか
- 今回やらないことが明確か

不安がある場合は、実装に進まず質問してください。

```text
この方針だと影響範囲が広そうです。
今回はもっと小さい範囲に分けられますか。
```

```text
対象ファイルを1つに絞る場合、どこから始めるのがよいですか。
```

## 実装を依頼するときの例

計画に納得できたら、実装を依頼します。

```text
方針は問題なさそうです。
今回は [対象ファイル名] に絞って修正してください。
修正後に、差分と確認方法を説明してください。
```

## 修正後に確認すること

修正が終わったら、AIの説明だけでなく、実際の差分を見ます。

確認観点:

- 依頼した目的に合っているか
- 余計なファイルを触っていないか
- 小さな修正なのに過剰な変更になっていないか
- 既存の文体、命名、ルールに合っているか
- テストや動作確認の説明が妥当か

分からない変更があれば、こう聞いてください。

```text
この変更の意図を、変更前後の違いが分かるように説明してください。
```

## 最後に聞くとよいこと

採用する前に、リスクや見落としをもう一度聞きます。

```text
この変更について、見落としやリスク、反対意見があれば挙げてください。
存在しない仕様やファイルを前提にしていないかも確認してください。
```

## 止めてよいサイン

次のような場合は、作業を進めずに止めてください。

- 触るファイルが予想より多い
- 削除や大きな移動を提案された
- `git reset`、`git clean`、`git rebase`、force pushなどを提案された
- 本番環境、DB、秘密情報に関係しそう
- AIの説明がよく分からない
- なんとなく不安がある

止めるときの例:

```text
この操作は影響が大きそうなので、ここで止めます。
安全な代替案と、相談すべき相手を整理してください。
```

## 説明会のあとにやること

できれば、自分の担当範囲で小さな候補を1つ選び、変更前の計画確認まで試してみてください。

実装まで進めなくても構いません。
「どのファイルを触る予定か」「どう確認するか」「どんなリスクがあるか」をAIに整理してもらうだけでも練習になります。

試した結果は、次回以降のチーム運用づくりに使います。

- うまくいった依頼文
- 分かりにくかった点
- 危なそうだと感じた提案
- テストや確認方法で迷った点

小さな気づきを共有して、チームのルールやFAQに育てていきます。
