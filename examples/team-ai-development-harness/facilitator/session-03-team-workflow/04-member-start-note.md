# 第3回 参加者向けメモ: チームの運用にする

このメモは、第3回「チームの運用にする」の事前・事後に参加者へ共有するためのものです。

## 今日の目的

Claude Codeの使い方を、個人の試行錯誤で終わらせず、チームで安全に続ける運用にします。

決めることは、主に次の4つです。

- 相談先
- レビュー観点
- 承認が必要な作業
- つまずきやヒヤリハットの共有方法

## 事前に考えておくこと

第2回以降に試したこと、または試せなかった理由を1つ持ってきてください。

例:

- 便利だった依頼文
- 不安だったAIの提案
- 差分確認で迷った点
- テストや動作確認で迷った点
- どこまで自分で進めてよいか分からなかった作業

## チームで決めたいこと

### 相談先

迷ったときに誰へ聞くかを決めます。

```text
まず聞く相手:
技術的に見る相手:
本番影響やセキュリティを見る相手:
```

### レビュー観点

AIが作った変更を見るときは、最低限次を確認します。

- 依頼した目的に合っているか
- 余計なファイルを触っていないか
- 既存の文体、命名、設計に合っているか
- テストや動作確認の方法が妥当か
- リスクや不明点が説明されているか

### 承認が必要な作業

個人で試しやすいもの:

- 変更前の調査
- 実装方針の整理
- READMEや手順書の小さな補足
- 文言修正
- テスト追加候補の洗い出し

相談してから進めるもの:

- 複数ファイルにまたがる変更
- 仕様や設計に関わる変更
- 認証、権限、DB、セキュリティに関わる変更
- 削除や大きな移動
- `git reset`、`git clean`、`git rebase`、force pushなど
- 本番環境や本番DBへの操作

## つまずき共有ログ

長い報告書にする必要はありません。
次の形で短く共有します。

```text
何を頼んだか:
AIが何を提案したか:
どこで迷ったか:
最終的にどう判断したか:
次回のために残す一言:
```

## 共有してよいこと

- うまくいった依頼文
- AIが出した危なそうな提案
- 差分確認で分からなかったこと
- テストや動作確認で迷ったこと
- 「ここで止めてよかった」という判断

ヒヤリハットは、個人を責めるためではなく、同じ不安を次の人が避けるために共有します。

## 運用メモの雛形

チームで最初に作る運用メモは、次のくらいの軽さで十分です。

```text
# Claude Code チーム運用メモ

## 相談先

- まず聞く相手:
- 技術的に見る相手:
- 本番影響やセキュリティを見る相手:

## 個人で試してよい範囲

-

## レビュー必須の範囲

-

## 危ない操作の例

-

## 共有ログの置き場所

-

## まず使う依頼文

-
```

## 説明会のあとにやること

チームで運用メモの初版を作り、まず1週間だけ試してみてください。

試したあとに、次のどれかを1つ共有します。

- 便利だった依頼文
- 迷った判断
- 危なそうだと感じた提案
- レビューで見落としそうになった点

小さく試して、小さく直す。運用もコードと同じように育てていきます。
