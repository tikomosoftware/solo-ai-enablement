# AI開発利用ポリシー 共通ルール

## 目的

このドキュメントは、エンジニアが業務でAI開発支援ツールを使うときの共通ルールを定めるものです。

AIは開発効率を上げる強力な道具ですが、最終的な設計判断、品質判断、セキュリティ判断、リリース判断は人間のエンジニアが行います。

## 基本方針

- AIは開発者の補助として使う。
- AIの出力をそのまま正解として扱わない。
- 生成されたコード、設定、ドキュメントは必ず人間が確認する。
- 機密情報、個人情報、顧客情報、認証情報をAIに入力しない。
- 影響範囲が大きい変更は、AIに任せる前に人間が方針を決める。
- 削除、履歴改変、force push、本番環境操作はAIに任せない。
- AIを使った変更でも、通常のレビュー、テスト、承認フローを省略しない。

## AIに任せてよい作業

次の作業はAIに依頼してよいものとします。

- コードベースの調査
- 既存コードの説明
- エラー原因の調査
- 小さな修正案の作成
- テストケースのたたき台作成
- READMEや開発メモの下書き
- リファクタリング方針の提案
- レビュー観点の洗い出し
- 型定義、関数、クラス、コンポーネントの下書き
- SQL、正規表現、シェルコマンドの相談

ただし、AIが作った内容は必ず確認し、必要に応じて修正します。

## AIに任せない作業

次の作業は、AIに単独で任せてはいけません。

- 本番環境へのデプロイ
- 本番データの変更、削除、移行
- データベースのdrop、truncate、reset
- destructive migrationの実行
- `git reset`、`git clean`、`git rebase`
- `git push --force`、`git push --force-with-lease`
- 認証、認可、課金、個人情報処理の最終判断
- セキュリティ仕様の最終判断
- ライセンス、契約、法務に関わる判断
- 顧客向け回答の最終確定
- 大量ファイル削除、大量移動、大量リネーム

AIがこれらの作業を提案した場合は、実行せず、人間が影響範囲を確認します。

## 入力してはいけない情報

次の情報は、許可された環境でない限りAIに入力しません。

- `.env` の値
- APIキー
- アクセストークン
- パスワード
- 秘密鍵、証明書
- 顧客名、担当者名、連絡先
- 個人情報
- 契約情報
- 未公開の売上、原価、経営情報
- セキュリティインシデントの詳細
- 脆弱性情報
- 本番ログの生データ
- 非公開の顧客データ

必要な場合は、値を伏せる、ダミーデータに置き換える、抽象化して相談します。

## AI利用時の標準フロー

AIに実装を依頼する場合は、次の流れを基本とします。

1. 目的を説明する。
2. 変更してよい範囲を指定する。
3. 変更してはいけない範囲を指定する。
4. まず調査だけを依頼する。
5. 変更方針を確認する。
6. 実装を依頼する。
7. 差分を確認する。
8. テスト、ビルド、lintを実行する。
9. 人間がレビューしてからコミットする。

最初から「全部やって」と依頼するのではなく、調査、方針、実装、確認を分けます。

## 推奨プロンプト

実装前の調査:

```text
まず関連ファイルを調査してください。
変更はまだ行わず、影響範囲、変更候補、確認すべきリスクを整理してください。
```

小さな実装:

```text
以下の変更を実装してください。
条件:
- 変更範囲は最小限にする
- 既存の設計と命名に合わせる
- 依頼範囲外のリファクタリングはしない
- 実装後に実行すべきテストを提案する
```

レビュー:

```text
この差分をレビューしてください。
観点:
- バグの可能性
- セキュリティリスク
- 既存仕様の破壊
- テスト不足
- 不要な変更
```

危険操作の制限:

```text
削除、reset、clean、rebase、force push、本番環境への操作は行わないでください。
必要だと判断した場合は、実行せず、理由と影響範囲だけ説明してください。
```

## 共通のレビュー観点

AIを使った変更では、特に次を確認します。

- 依頼した範囲だけが変更されているか
- 既存仕様を壊していないか
- 例外処理が不足していないか
- エラー時の挙動が適切か
- セキュリティ上の問題がないか
- 認証、認可、入力検証が適切か
- テストが必要な箇所にテストがあるか
- ログに機密情報が出ないか
- 不要な依存関係を追加していないか
- コード規約に合っているか

## コミットとプルリクエスト

AIを使った変更でも、コミットとプルリクエストは通常の開発フローに従います。

コミット前:

- `git status --short` を確認する。
- 差分を確認する。
- 不要なファイルが含まれていないか確認する。
- テストやビルドの結果を確認する。

プルリクエスト:

- AIを使った場合でも、人間が変更内容を説明できる状態にする。
- 変更理由、影響範囲、確認内容を書く。
- 生成コードのまま提出せず、レビューしやすい単位にする。

## 事故を防ぐための運用

チームでは、次の運用を推奨します。

- AIで便利だった使い方を共有する。
- AIが間違えた例も共有する。
- 危険だったプロンプトを共有する。
- `CLAUDE.md` や `.claude/settings.json` を定期的に見直す。
- 新しいAI機能を使う前に、情報管理と権限を確認する。
- 重要な変更はAIではなく人間が主導する。

## このポリシーの見直し

AIツールは頻繁に変わります。

このポリシーは固定ではなく、実際の利用状況、事故例、チームの成熟度に合わせて見直します。
