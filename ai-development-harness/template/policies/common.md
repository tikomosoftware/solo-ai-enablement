# AI開発利用ポリシー 共通ルール

## このポリシーの目的

このポリシーは、エンジニアがAI開発支援ツールを仕事で使うときの共通ルールです。

対象ツールは、Claude Code、GitHub Copilot、GitHub Copilot CLI、その他のAIコーディング支援ツールを想定します。

AIは開発効率を上げるための補助ツールです。最終的な設計判断、品質判断、セキュリティ判断、リリース判断は人間の開発者とチームが行います。

## 基本方針

- AIは開発者の補助として使います。
- AIの出力をそのまま正解として扱いません。
- 生成されたコード、設定、ドキュメントは必ず人間が確認します。
- 機密情報、個人情報、顧客情報、認証情報をAIに入力しません。
- 削除、履歴改変、force push、本番環境操作はAIに任せません。
- AIを使った変更でも、通常のレビュー、テスト、承認フローを省略しません。
- AIを使った本人が、変更内容を説明できる状態にします。

## 最初に守ること

AIを使う前に、次を確認してください。

- 対象リポジトリのプロジェクトルートで起動している。
- `CLAUDE.md` が読み込まれている。
- `.claude/settings.json` の権限設定が効いている。
- 入力してはいけない情報を渡していない。
- 変更してよい範囲と、変更してはいけない範囲を説明できる。

Claude Codeを使う場合は、初回に次を確認します。

```text
/memory
/permissions
```

## AIに任せてよい作業

次の作業は、AIに依頼してよいものとします。

- コードベースの調査
- 既存コードの説明
- エラー原因の調査
- 小さな修正案の作成
- テストケースのたたき台作成
- READMEや開発メモの下書き
- リファクタリング方針の提案
- レビュー観点の洗い出し
- テスト観点の洗い出し
- コマンドや設定ファイルの意味の説明

ただし、AIの回答や生成物は必ず人間が確認します。

## AIに任せない作業

次の作業は、AIに単独で任せてはいけません。

- 本番環境へのデプロイ
- 本番データの変更、削除、移行
- データベースのdrop、truncate、reset
- destructive migrationの実行
- `git reset`、`git clean`、`git rebase`
- `git push --force`、`git push --force-with-lease`
- 認証、認可、課金、個人情報処理の最終判断
- セキュリティ仕様の最終判断
- ライセンス、契約、法務に関わる判断
- 顧客向け回答の最終確定
- 大量ファイル削除、大量移動、大量リネーム

AIがこれらを提案した場合は、実行せず、人間が影響範囲を確認します。

## 入力してはいけない情報

次の情報は、許可された環境でない限りAIに入力しません。

- `.env` の値
- APIキー
- アクセストークン
- パスワード
- 秘密鍵、証明書
- 顧客名、担当者名、連絡先
- 個人情報
- 契約情報
- 未公開の売上、原価、経営情報
- セキュリティインシデントの詳細
- 脆弱性情報
- 本番ログの生データ
- 非公開の顧客データ

必要な場合は、値を伏せる、ダミーデータに置き換える、抽象化して相談します。

## 事前承認が必要な操作

次の操作は、AIに実行させる前に人間の承認が必要です。

- ファイル移動
- ファイルリネーム
- 大量置換
- 大量フォーマット
- 依存パッケージ追加
- lockfileの大きな変更
- マイグレーション作成
- CI/CD設定変更
- Dockerfile変更
- インフラ設定変更
- 通常の `git commit`
- 通常の `git push`

承認時には、対象、理由、影響範囲、戻し方を確認します。

## 標準フロー

AIに実装を依頼する場合は、次の流れを基本とします。

1. 目的を説明する。
2. 変更してよい範囲を指定する。
3. 変更してはいけない範囲を指定する。
4. まず調査だけを依頼する。
5. 変更方針を確認する。
6. 実装を依頼する。
7. 差分を確認する。
8. テスト、ビルド、lintを実行する。
9. 人間がレビューしてからコミットする。

最初から「全部やって」と依頼しません。調査、方針、実装、確認を分けます。

## レビュー時に確認すること

AIを使った変更では、特に次を確認します。

- 依頼した範囲だけが変更されている。
- 既存仕様を壊していない。
- 例外処理が不足していない。
- エラー時の挙動が適切である。
- セキュリティ上の問題がない。
- 認証、認可、入力検証が適切である。
- テストが必要な箇所にテストがある。
- ログに機密情報が出ない。
- 不要な依存関係を追加していない。
- コード規約に合っている。

## よく使う依頼の型

調査:

```text
まず関連ファイルを調査してください。
変更はまだ行わず、影響範囲、変更候補、確認すべきリスクを整理してください。
```

実装:

```text
以下の変更を実装してください。
条件:
- 変更範囲は最小限にする
- 既存の設計と命名に合わせる
- 依頼範囲外のリファクタリングはしない
- 実装後に実行すべきテストを提案する
```

レビュー:

```text
この差分をレビューしてください。
観点:
- バグの可能性
- セキュリティリスク
- 既存仕様の破壊
- テスト不足
- 不要な変更
```

危険操作の制限:

```text
削除、reset、clean、rebase、force push、本番環境への操作は行わないでください。
必要だと判断した場合は、実行せず、理由と影響範囲だけ説明してください。
```

## 事故やヒヤリハットの共有

AI利用で危ない提案、誤った説明、不要な変更、機密情報に触れそうな挙動があった場合は共有します。

共有の目的は、誰かを責めることではありません。同じ失敗をチームで繰り返さないために、FAQ、権限設定、チェックリストを改善することです。

共有には `templates/incident-report.md` を使います。
