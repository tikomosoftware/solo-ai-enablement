# リポジトリ導入手順

## 目的

このドキュメントは、既存リポジトリにAI Development Harnessを導入する手順です。

## 手順1: 対象リポジトリを決める

最初は、影響範囲が読みやすいリポジトリから始めます。

避けたいもの:

- 本番データに直結するリポジトリ
- 秘密情報が多いリポジトリ
- リリース直前のリポジトリ
- 変更が激しいリポジトリ

## 手順2: harnessをコピーする

`ai-development-harness/template/` の中身を、対象リポジトリのプロジェクトルートへコピーします。

配置例:

```text
my-app/
  CLAUDE.md
  .claude/
    settings.json
  docs/
  policies/
  workflows/
  checklists/
  prompts/
```

## 手順3: プロジェクト向けに調整する

最低限、次を編集します。

- `CLAUDE.md`
- `.claude/settings.json`
- `policies/common.md`
- 担当領域に合う `policies/*.md`
- `docs/start-guide.md`

このとき、`templates/project-adoption-profile.md` をコピーして、プロジェクト固有の情報を埋めます。

整理する内容:

- 実際のテストコマンド
- 実際のビルドコマンド
- ブランチ運用
- PRルール
- 使用してよいAIツール
- 入れてはいけない情報の組織内基準
- 相談先
- 具体的な対象リポジトリ

`policies/common.md` は全プロジェクトで残します。`frontend.md`、`backend.md`、`windows-app.md`、`devops.md`、`qa.md` は、プロジェクトの技術領域に合わせて残す、削る、または追記します。

## 手順4: チームでレビューする

harnessの導入は、通常のコード変更と同じようにPRでレビューします。

レビュー観点:

- 禁止操作が十分か。
- 権限設定が厳しすぎないか。
- プロジェクト固有の注意点が入っているか。
- テストやビルドコマンドが正しいか。
- 情報管理ルールが明確か。

## 手順5: 初回説明会を行う

説明会ではすべての資料を説明しません。

説明するもの:

- harnessの考え方
- プロジェクトルートで起動すること
- VS Codeのmulti-rootを避けること
- 禁止操作
- 最初の実践課題

## 手順6: 小さく試す

最初は変更なしの調査から始めます。

次に、小さな修正で試します。

例:

- README修正
- テスト追加
- 文言修正
- 小さなバグ修正

## 手順7: ふりかえりで更新する

1〜2週間使ったら、ルールを見直します。

確認すること:

- よく使うプロンプトは何か。
- 危険だった操作は何か。
- FAQに追加すべき質問は何か。
- 権限設定を変更すべきか。
- 職種別ポリシーに不足はないか。
