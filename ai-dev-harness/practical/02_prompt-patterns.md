# 02. 依頼文の基本パターン

## この章の目的

実務で繰り返し使う依頼文の型をまとめます。

依頼文は長く複雑にする必要はありません。目的、制約、確認してほしいこと、変更してよい範囲を明確にします。

## 調査を依頼する

```text
この機能の実装場所と処理の流れを調査してください。
まだファイルは変更しないでください。
関連ファイル、主要な関数、影響しそうな箇所を整理してください。
```

使う場面:

- 初めて触る機能を理解したいとき
- 不具合の原因候補を知りたいとき
- 修正前に影響範囲を見たいとき

## 実装方針を出してもらう

```text
この修正を行う場合の実装方針を提案してください。
まだ変更はしないでください。
変更予定ファイル、影響範囲、確認方法、リスクを短く整理してください。
```

使う場面:

- 実装前に触る範囲を確認したいとき
- 変更が大きくなりそうか見極めたいとき

## 小さな修正を依頼する

```text
方針に沿って、影響範囲の小さい修正だけを行ってください。
依頼範囲外のリファクタリングや整形はしないでください。
変更後に、差分の要約と確認方法を教えてください。
```

使う場面:

- README追記
- 文言修正
- 小さなバグ修正
- テスト追加

## 差分説明を依頼する

```text
現在の差分をレビューしやすいように説明してください。
変更した目的、主な変更点、影響範囲、確認すべき点を整理してください。
```

使う場面:

- PR前
- レビュー依頼前
- 自分で差分を読み直す前

## レビュー観点を出してもらう

```text
この差分について、レビュー観点を洗い出してください。
バグの可能性、仕様の見落とし、テスト不足、既存設計とのズレを優先して見てください。
```

使う場面:

- 人間レビューの前
- 自分の見落としを減らしたいとき

## テスト確認を依頼する

```text
この変更に対して必要なテストや動作確認を整理してください。
実行すべきコマンド、手動確認の観点、確認できない場合のリスクを分けてください。
```

使う場面:

- 修正後
- PR前
- テストが足りるか不安なとき

## 困ったときに止める

```text
ここで作業を止めてください。
現在の状態、変更済みファイル、未確認の点、次に人間が判断すべきことを整理してください。
```

使う場面:

- 提案が大きくなりすぎたとき
- 差分が読めなくなったとき
- 危険操作が出てきたとき
