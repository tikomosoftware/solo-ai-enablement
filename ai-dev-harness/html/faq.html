AI開発支援 FAQ

AIが間違えたら誰の責任ですか

最終責任は人間の開発者とチームにあります。

AIは補助ツールです。AIが出したコード、説明、コマンド、判断材料は必ず人間が確認します。

コードをAIに読ませていいですか

所属組織で許可された環境、対象リポジトリ、ツールであれば利用できます。

ただし、顧客情報、個人情報、秘密情報、未公開情報が含まれる場合は、入力してよいか確認してください。

.env は見せていいですか

原則として見せてはいけません。

必要な場合は、値を伏せて環境変数名だけ説明します。

APIキーやトークンを貼っていいですか

貼ってはいけません。

ログやエラーに含まれている場合も、伏せてから相談します。

VS Codeのmulti-root workspaceは使っていいですか

最初は使わないことを推奨します。

1つのVS Codeウィンドウには、1つのプロジェクトルートだけを開いてください。

Claude CodeはPC全体を見ますか

Claude Codeは、起動したフォルダを中心に作業します。

ただし、OSレベルで完全に隔離されているわけではありません。広いフォルダで起動すると、関係ないファイルまで見えてしまう可能性があります。

必ず対象リポジトリのプロジェクトルートで起動してください。

CopilotとClaude Codeはどう使い分けますか

短い補完やエディタ内の小さな相談はGitHub Copilotが向いています。

リポジトリ調査、複数ファイル修正、テスト実行を含む作業はClaude Codeが向いています。

詳しくは docs/tool-selection-guide.md を見てください。

AIが削除を提案したらどうしますか

すぐに実行しません。

対象パス、理由、影響範囲を確認し、人間が判断します。最初の運用では、削除はAIに実行させない方針を推奨します。

force pushはAIに任せていいですか

任せてはいけません。

git push --force や git push --force-with-lease はリモート履歴を書き換える可能性があります。

AIが作ったコードはレビュー不要ですか

レビューが必要です。

AIを使った変更でも、人間が書いたコードと同じレビュー、テスト、承認フローを通します。

AI利用をPRに書く必要がありますか

チーム方針によりますが、最初は書くことを推奨します。

少なくとも、変更内容を人間が説明できる状態にしてください。

何から始めればいいですか

docs/first-exercise.md の最初の課題から始めてください。

最初はコードを変更せず、調査とルール確認だけを行います。

Claude Codeを起動する場所が分かりません

対象リポジトリのプロジェクトルートで起動します。

プロジェクトルートは、VS Codeで「フォルダーを開く」ときに選ぶ一番上のフォルダです。

よい例:

cd C:\ProjectsDEV\my-app
claude --permission-mode default

避ける例:

cd C:\
claude
cd C:\ProjectsDEV
claude

VS Codeで複数プロジェクトを開いています。このままでいいですか

最初は避けてください。

1つのVS Codeウィンドウには、1つのプロジェクトルートだけを開く運用を推奨します。複数プロジェクトを同時に開くと、Claude Codeがどのフォルダを作業対象にしているか分かりにくくなります。

Claude Codeが別プロジェクトのファイルを見ている気がします

起動した場所を確認してください。

PowerShell:

Get-Location

Claude Codeを終了し、対象リポジトリのルートへ移動してから起動し直します。

/memory でCLAUDE.mdが出てきません

CLAUDE.md がプロジェクトルートにあるか確認してください。

また、Claude Codeをプロジェクトルートで起動しているか確認してください。

/permissions で想定した設定になっていません

.claude/settings.json がプロジェクトルート配下にあるか確認してください。

配置例:

my-app/
  .claude/
    settings.json
  CLAUDE.md

permission modeは何を使えばいいですか

最初は plan か default を使います。

  • plan: 調査や方針整理だけしたいとき
  • default: 通常利用。編集やコマンド実行で確認が入りやすい

bypassPermissions は通常の実務リポジトリでは使いません。

AIにcommitしてもらっていいですか

最初の運用では、人間が明示的に依頼した場合だけにします。

AIにcommitさせる場合でも、事前に git status --short と差分を人間が確認してください。

AIにpushしてもらっていいですか

最初の運用では、pushは人間が行うことを推奨します。

特にforce pushはAIに任せてはいけません。

AIにファイル移動やリネームを頼んでいいですか

必要な場合は、事前に対象パス、理由、影響範囲を説明させ、人間が確認してからにします。

最初は、AIに提案だけさせて、人間が実行する運用が安全です。

AIに依存パッケージを追加してもらっていいですか

事前承認が必要です。

依存追加は、セキュリティ、ライセンス、bundle size、lockfile変更、メンテナンス性に影響します。

AIが「テストは不要」と言っています。信じていいですか

そのまま信じません。

テスト不要の判断は人間が行います。少なくとも、なぜ不要なのか、既存テストでどこが担保されるのかを確認します。

AIが作ったコードが動けばOKですか

動くだけでは不十分です。

既存設計に合っているか、保守しやすいか、セキュリティリスクがないか、テストがあるかを確認します。

AIが知らないライブラリを使おうとしています

勝手に採用しないでください。

既存プロジェクトで使っているライブラリや標準的な方法に合わせます。新規ライブラリが必要な場合は、人間が判断します。

AIに本番ログを貼っていいですか

原則として貼りません。

必要な場合は、個人情報、顧客情報、トークン、IPアドレス、メールアドレスなどを除去またはマスクしてから相談します。

AIにエラー画面のスクリーンショットを見せていいですか

機密情報、顧客名、個人情報、URL、トークン、非公開情報が写っていないか確認してください。

写っている場合はマスクします。

AIを使ったことを隠してPRを出していいですか

チーム方針によりますが、最初はAIを使ったことを共有する方針を推奨します。

目的は責めることではなく、レビュー観点を合わせるためです。

AIの回答が自信満々ですが、根拠が分かりません

根拠を確認してください。

その説明の根拠となるファイル、行、公式ドキュメント、またはテスト結果を示してください。

根拠が出せない場合は、参考意見として扱います。

AIが途中で関係ないリファクタリングを始めました

止めます。

依頼範囲外のリファクタリングは行わないルールです。差分を確認し、必要なら元に戻す方針を人間が判断します。

AIの提案が速すぎてレビューが追いつきません

作業を小さく分けます。

一度に編集せず、まず変更方針と対象ファイルだけ提示してください。
1ファイルずつ変更してください。

どんな失敗を共有すればいいですか

実害が出たものだけでなく、ヒヤリとしたものも共有します。

例:

  • 危険なコマンドを提案した
  • 不要なファイルを編集した
  • .env を読もうとした
  • 仕様を勘違いした
  • テストなしで完了と言った
  • 存在しないAPIを使った
  • 依頼していないリファクタリングを始めた

共有には templates/incident-report.md を使います。

Skillsは最初から作るものですか

必ず最初から作る必要はありません。

Skillsは、Claudeに特定の作業をうまくやってもらうための再利用パッケージです。

最初から作ってよいSkillもあります。

例:

  • コードレビュー
  • テスト観点洗い出し
  • PR説明文作成
  • リリースノート作成

一方で、後から作った方がよいSkillもあります。

例:

  • プロジェクト固有のデプロイ手順
  • 組織固有のレビュー観点
  • 独自ライブラリの使い方
  • よくある障害対応

初期導入では、まず prompts/ や workflows/ に作業の型を置きます。

運用していく中で、何度も使うもの、毎回同じ説明をしているもの、チームで標準化したいものが見えてきたらSkills化します。

つまり、Skillsは最初から作ってもよいですが、運用で溜まったノウハウを後からまとめるものでもあります。

今回のharnessやルールファイルはSkillsですか

同じものではありません。

関係は次のように考えます。

CLAUDE.md
  プロジェクトで守るルール、前提、作業方針

.claude/settings.json
  許可、確認、禁止する操作の設定

policies / workflows / checklists / prompts
  チームで共有する運用資料、手順、テンプレート

Skills
  特定の作業をClaudeにうまくやらせるための再利用パッケージ

Harness
  それらをまとめて、チームで安全にAIを使うための上位構造

今回のharnessはSkillsそのものではありません。

ただし、prompts/ や workflows/ は、将来的にSkills化できる材料です。
