AI Development Harnessの考え方

Harnessとは何か

AI Development Harnessとは、AIに開発作業を任せる前に、作業範囲、権限、進め方、確認方法を整えるための仕組みです。

AIに「この機能をいい感じに作って」と依頼すると、AIは広い範囲を調べ、ファイルを編集し、コマンドを実行しようとします。これは便利ですが、チーム開発では危険もあります。

そこで、AIが動く前に作業環境を整えます。これがharnessの考え方です。

なぜ必要か

チーム開発では、一人の判断で作業が完結することはほとんどありません。

実際の開発には、次のような前提があります。

  • 既存の設計がある
  • チームのコーディング規約がある
  • レビューと承認フローがある
  • 触ってよい範囲と触ってはいけない範囲がある
  • 本番環境や顧客データを守る必要がある
  • 複数人が同じリポジトリで作業している

AIを個人の便利ツールとしてだけ使うと、これらの前提が抜け落ちやすくなります。

Harnessは、AI活用を個人技ではなく、チームの開発プロセスに乗せるための考え方です。

4つの要素

Harnessは、次の4つに分けると考えやすくなります。

1. Context

Contextは、AIに渡す前提情報です。

例:

  • プロジェクト概要
  • アーキテクチャ
  • コーディング規約
  • 命名ルール
  • テスト方針
  • 変更してよい範囲
  • 変更してはいけない範囲

このリポジトリでは、主に次がContextになります。

CLAUDE.md
README.md
docs/
policies/
workflows/

AIは文脈が不足すると、一般論で判断します。チームの事情を反映するには、Contextを明示する必要があります。

2. Guardrails

Guardrailsは、AIに許可すること、確認が必要なこと、禁止することを決める仕組みです。

例:

  • .env を読ませない
  • 秘密鍵を読ませない
  • ファイル削除を禁止する
  • force pushを禁止する
  • ファイル編集は確認する
  • 本番環境操作はAIに任せない

このリポジトリでは、主に次がGuardrailsになります。

.claude/settings.json
policies/common.md
checklists/

CLAUDE.md に「やらないで」と書くだけでは、強制力としては不十分です。実際に止めたい操作は、権限設定やレビュー運用で止めます。

3. Workflow

Workflowは、AIと人間がどう作業を進めるかを決めるものです。

例:

  • まず調査する
  • 変更方針を説明する
  • 人間が確認する
  • 実装する
  • テストする
  • 差分を報告する
  • PRを作る

このリポジトリでは、主に次がWorkflowになります。

workflows/
prompts/

AIにいきなり実装させるのではなく、調査、計画、実装、確認を分けることで事故を減らします。

4. Verification

Verificationは、AIの作業結果をどう確認するかです。

例:

  • npm run test
  • npm run build
  • lint
  • 型チェック
  • コードレビュー
  • セキュリティ観点レビュー
  • PRチェックリスト

このリポジトリでは、主に次がVerificationになります。

checklists/
workflows/code-review.md
workflows/pull-request.md

AIが作ったコードも、人間が作ったコードと同じように確認します。むしろ、AI生成物は一見きれいに見えるぶん、意図しない仕様変更やセキュリティリスクを見落としやすいことがあります。

チームで共有する意味

Harnessは、個人のローカルメモではなく、チームで共有することに意味があります。

チームで共有すると、次の効果があります。

  • AIの使い方が人によって大きくばらつかない
  • 危険操作のルールを統一できる
  • 新しいメンバーが始めやすい
  • レビュー観点をそろえられる
  • 失敗例や改善をチーム資産にできる

AIを使う人だけが詳しくなる状態を避け、チーム全体で安全に使える状態を作ります。

最初から完璧にしない

Harnessは、最初から完璧なルール集を作るものではありません。

最初は次の最小構成で十分です。

CLAUDE.md
.claude/settings.json
docs/start-guide.md
policies/common.md
checklists/before-ai-work.md

実際に使いながら、足りないルール、よく使うプロンプト、失敗しやすい作業を追加していきます。

Skillsはいつ作るか

Claude CodeにはSkillsという考え方があります。

Skillsは、特定の作業をClaudeにうまく実行してもらうための再利用パッケージです。harnessそのものがSkillというわけではありません。

チーム導入では、Skillsは最初から必須ではありません。

最初からSkill化してよいもの:

  • コードレビュー
  • テスト観点洗い出し
  • PR説明文作成
  • リリースノート作成

後からSkill化するのが向いているもの:

  • プロジェクト固有のデプロイ手順
  • 組織固有のレビュー観点
  • 独自フレームワークや組織内ライブラリの使い方
  • よくある障害対応

最初は、prompts/ と workflows/ に作業の型を置きます。

実運用で何度も使うもの、毎回同じ説明をしているもの、チームで標準化したいものが見えてきたら、それをSkills化します。

つまり、harnessはSkillsを含めて安全に使うための上位構造であり、Skillsはharnessの中で育っていく再利用部品です。

このサンプルの位置づけ

この ai-development-harness は、チームでAI開発支援を始めるためのテンプレートです。

そのまま使うのではなく、各プロジェクトの事情に合わせて編集してください。

重要なのは、フォルダ構成そのものよりも、次の考え方です。

AIに作業させる前に、仕事場を整える。
AIの出力を、チームの開発プロセスの中で検証する。
