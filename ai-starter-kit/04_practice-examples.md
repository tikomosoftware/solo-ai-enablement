# 04. AI初心者向け 実践例インデックス

## このファイルの目的

このファイルは、AIを仕事で使い始める人が、最初に試しやすい実践例をまとめた入口です。

1から9までの記事では、AI活用の基本的な考え方、注意点、ルールを整理しました。ここでは、実際にどんな依頼文を使えばよいか、返ってきた内容をどこで確認すればよいかを、具体的な場面ごとに整理します。

Before / After形式の実例集は別資料としてまとめるため、このファイルでは、すぐ試せる依頼文、確認ポイント、追加依頼の例を扱います。

## 使う前の共通ルール

どの実践例でも、次のルールを守ります。

- 顧客名、個人名、メールアドレス、電話番号をそのまま入れない
- 契約情報、売上、未公開情報、認証情報を入れない
- 実データを使う必要がなければ、ダミー情報に置き換える
- AIの出力はそのまま提出せず、人間が確認する
- 数字、日付、固有名詞、約束してよい内容は必ず見直す

## 実践例1: チーム内チャット文を作る

使う場面:

- 会議時間の変更を知らせる
- 作業依頼を丁寧に伝える
- 共有事項を短くまとめる

入力例:

```text
以下の内容を、チーム内チャットに投稿する短い文面にしてください。
丁寧だけど堅すぎない表現にしてください。

内容:
- 明日の定例会の開始時間を変更する
- 変更前: 10:00
- 変更後: 11:00
- 理由: 先方都合
- 対象: プロジェクトメンバー

条件:
- 短くする
- 申し訳なさを出しすぎない
- 最後に確認してほしいことを入れる
```

確認ポイント:

- 時刻が間違っていないか
- 理由を言いすぎていないか
- 相手に冷たく見えないか
- 自分たちのチームの言い方として自然か

追加依頼の例:

```text
もう少しくだけた社内向けの表現にしてください。
ただし、失礼にはならないようにしてください。
```

## 実践例2: 会議メモを整理する

使う場面:

- 会議後のメモを整理する
- 決定事項とTODOを分ける
- 未決事項を見落とさないようにする

入力例:

```text
以下の会議メモを整理してください。
出力は「決定事項」「TODO」「未決事項」「次回確認すること」に分けてください。
TODOには担当者と期限の欄を作ってください。

会議メモ:
[ここに機密情報を含まないメモ、またはダミー化したメモを貼る]
```

確認ポイント:

- 決定していないことを決定事項にしていないか
- 担当者や期限をAIが勝手に作っていないか
- 重要な論点が落ちていないか
- 元のメモにない情報を追加していないか

追加依頼の例:

```text
決定事項と推測を分けてください。
元のメモから確認できない内容は「要確認」と書いてください。
```

## 実践例3: 長い文章を要約する

使う場面:

- 長い案内文の要点をつかむ
- 資料の概要を短くする
- 忙しい人向けの共有文を作る

入力例:

```text
以下の文章を、3行の要約と重要ポイント5つに分けて整理してください。
対象読者は、このテーマに詳しくない組織内メンバーです。

条件:
- 断定しすぎない
- 元の文章にない情報を足さない
- 数字や日付はそのまま残す

文章:
[ここに要約したい文章を貼る]
```

確認ポイント:

- 数字、日付、固有名詞が変わっていないか
- 重要な条件が落ちていないか
- AIが元の文章にない説明を足していないか
- 要約だけ読んだ人が誤解しないか

追加依頼の例:

```text
この要約だけを読んだ人が誤解しそうな点を3つ挙げてください。
```

## 実践例4: 手順書のたたき台を作る

使う場面:

- 作業メモを手順書にする
- 新人や引き継ぎ向けの説明を作る
- よくあるミスや確認ポイントを整理する

入力例:

```text
以下の作業メモを、初めて作業する人向けの手順書にしてください。

出力:
- 目的
- 事前準備
- 手順
- 確認ポイント
- よくあるミス
- 困ったときの相談先

条件:
- 分からない点は勝手に補完せず「要確認」と書く
- 危険な操作がありそうな箇所は注意として分ける

作業メモ:
[ここに機密情報を含まない作業メモを貼る]
```

確認ポイント:

- 実際の作業順と合っているか
- AIが存在しない手順を足していないか
- 危険な操作が軽く扱われていないか
- 相談先や確認方法が現場に合っているか

追加依頼の例:

```text
初めて読む人がつまずきそうな箇所を挙げて、補足説明を追加してください。
```

## 実践例5: Excel関数やSQLを相談する

使う場面:

- Excel関数の書き方を聞く
- SQLの考え方を確認する
- エラー原因の候補を出してもらう

入力例:

```text
A列に日付、B列に売上があります。
月ごとの売上合計を出すExcel関数を教えてください。

条件:
- 実データは使わず、例の表で説明してください
- 関数の意味も短く説明してください
- うまく動かない場合に確認する点も教えてください
```

確認ポイント:

- 自分のExcelやスプレッドシートで実際に動くか
- 区切り文字や関数名が利用環境に合っているか
- 実データに個人情報や顧客情報を含めていないか
- 結果が期待値と合っているか

追加依頼の例:

```text
この関数がうまく動かない場合の原因候補を、確認しやすい順に出してください。
```

## 実践例6: 文章を相手に合わせて言い換える

使う場面:

- 専門的な説明を初心者向けにする
- 社外向けの表現を丁寧にする
- 冷たく見える文面をやわらかくする

入力例:

```text
以下の文章を、AIをまだ使ったことがない人にも分かるように言い換えてください。

条件:
- 専門用語はできるだけ避ける
- 不安をあおらない
- 仕事で小さく試せる前向きな表現にする

文章:
[ここに言い換えたい文章を貼る]
```

確認ポイント:

- 意味が変わっていないか
- 重要な注意点が弱くなりすぎていないか
- 相手に失礼な表現がないか
- 自分たちの言葉として自然か

追加依頼の例:

```text
もう少し短くしてください。
ただし、注意点は残してください。
```

## 実践例7: 抜け漏れやリスクを確認する

使う場面:

- 自分で書いた案を見直す
- 手順書の不足を探す
- 文章の誤解されそうな点を確認する

入力例:

```text
以下の文章について、同意する前に批判的に確認してください。

確認してほしいこと:
- 分かりにくい点
- 誤解されそうな点
- 足りない前提
- 事実確認が必要な点
- 相手に冷たく見える表現

出力:
- 最大5件
- 重要度 High / Medium / Low を付ける
- 修正案も短く書く

文章:
[ここに確認したい文章を貼る]
```

確認ポイント:

- AIの指摘が本当に必要か
- 細かすぎる好みの指摘ではないか
- 重要度が現場の感覚と合っているか
- 修正案をそのまま使っても問題ないか

追加依頼の例:

```text
High と Medium の指摘だけに絞って、修正版を作ってください。
```

## 実践記事を増やすときの型

今後、個別の実践記事を増やす場合は、次の型でそろえると読みやすくなります。

```markdown
# タイトル

## 使う場面

どんな仕事で使うか。

## 入力例

そのまま試せる依頼文。

## 確認ポイント

AIの出力を見るときに、人間が確認すること。

## 追加依頼の例

返ってきた内容を直すための依頼文。

## 注意点

情報管理、事実確認、表現調整など。
```
